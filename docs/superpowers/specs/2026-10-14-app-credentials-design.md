# App credentials: approved implementation scope

The user approved implementing the proposed app-scoped encrypted credential registry, isolated rotation/access history tests, preservation of existing keys/data and deployment to the existing Cloudflare service without EAS or Actions. This approval includes execution and deployment; no additional design or execution-method question is needed.

Use the existing owner Durable Object authority and app registration in D1. Add additive DO tables only. Existing GitHub and OTA keys remain byte-identical in their existing records; this change must not recreate keys, replace trust certificates or modify app policies. New credential payloads use AES-256-GCM envelope encryption: one DEK/version, separate nonce for payload and wrapped DEK, authenticated context binding owner/database/app/kind/version and key ID. KEK key ring resides in a Worker Secret, not SQL, public vars, source, logs or browser storage. Missing KEK fails closed only for the new registry.

Kinds: ios_distribution, ios_provisioning, android_keystore, app_store_connect, google_play, apns, fcm, firebase_android, firebase_ios. Each app has independently versioned bindings by kind. Explicit shared-provider keys may be registered independently to approved apps; provider scope is not claimed to be narrowed by Flora bindings. Registered files/private keys/passwords are write-only through the management API. Lists/history contain only safe metadata, hashes, byte lengths, format-verification state and timestamps. There is no raw export, provider key issuance/revocation, native build credential delivery or push-sending API in this implementation.

GET /api/apps/:appId/credentials returns {appId,configured,credentials,history}. POST on that path accepts {kind,label,expectedVersion,metadata,payload:{fileBase64,password?,keyAlias?,keyPassword?}}. POST /api/apps/:appId/credentials/disable accepts {kind,expectedVersion}. A replacement creates a new immutable version and atomically moves only that app/kind binding; a failed candidate leaves the active version unchanged. Disable stops Flora usage and keeps version/history; it does not revoke the provider key. Reasons are fixed server action labels, not arbitrary secret-bearing user text.

Limits: upload request 1,500,000 bytes, decoded file <=1MiB, PEM/Google JSON <=64KiB, encrypted payload accounting <=4MiB/app and <=16MiB/owner, <=20 stored versions per app/kind. Streaming/deadlines and existing bounded import admission apply. Auth+CSRF precede body consumption. Recheck current grant after every async parse/crypto and inside transactionSync; expectedVersion CAS and capacity checks are atomic.

For PKCS8 P-256 and RSA service accounts use runtime crypto import and derive safe fingerprints/metadata; validate exact fixed provider endpoints and app/project metadata conflicts. Firebase Android JSON is checked against supplied package and project identity. P12/JKS/mobileprovision/plist are initially stored unverified, clearly labeled as requiring signing-tool validation; no filename/header-only success claim. Uploaded does not mean provider authorized or a signing/push operation succeeded.

The hosted UI adds an app-selected credential panel under Settings and a direct navigation from app operations. Selecting a different app, logout, expiry or late async response clears file/password inputs and prevents another app's mutation/render. No localStorage/clipboard/raw preview. Upload and disable operate on explicit app ID and current revision. Existing public CONFIG remains separate.

Preservation verification uses production read-only app state, operations and automation snapshots plus existing signing key IDs/certificate fingerprints before and after. Tests use generated/synthetic keys on two synthetic apps; real native/store/push credentials are not discovered or imported automatically. Production smoke only reads the registry until the owner provides credentials through the UI. Existing PC Runner and Docker continue unchanged. Infrastructure additions are one secret binding on the existing Worker and bounded additive tables in its existing DO; no new billed product, plan or resource.
