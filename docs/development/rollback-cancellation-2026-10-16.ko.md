# 정상 설치 보고 후 자동 롤백 취소 — 2026-10-16

소규모 앱 보호의 2분 확인 대기 중 별도의 정상 설치 보고가 도착하면, 최초 실패 판단을 보존하면서 현재 표본을 다시 계산해 불필요한 롤백 게시를 취소한다. 이번 검증은 **실패한 설치 A가 회복한 경우가 아니라, 같은 앱·배포의 독립 설치 B가 정상 적용·재시작한 경우**다. A의 실패·차단 기록을 지우거나 B의 성공을 A의 회복으로 합치지 않는다.

Isso·Promise·Reward의 iOS·Android 여섯 조합에서 실제 실패 감지, 독립 설치의 정상 보고, 120초 재확인 후 취소와 관리자 화면 확인을 완료했다. 모든 네이티브 증거는 전용 iOS 시뮬레이터·Android 에뮬레이터 기준이며 물리 기기 증거가 아니다. EAS·GitHub Actions는 사용하지 않았다.

## 사용 방법과 판단의 의미

프로젝트 → **OTA 배포** → 해당 배포의 **기기별 적용 현황**에서 자동 롤백 판단과 설치별 상세 이벤트를 함께 확인한다. 최초 실패 보고로 기준을 충족하면 **2분 복구 확인 대기**가 표시된다. 정상 보고 또는 추가 설치 보고로 기준이 더 이상 충족되지 않으면 **실패 기준 미충족으로 자동 롤백 취소**가 된다. 이 취소 상태 자체가 정상 실행을 증명하는 것은 아니다.

새 취소 기록은 다음을 분리해서 표시한다.

- **최초 감지:** 실패 1/1·100%, 당시 정책 버전과 최초 사유를 그대로 보존한다.
- **취소 시 재확인:** 실패 1/2·50%, 서버 재확인 시각(KST), 실제 정상 실행 확인 설치 수를 표시한다.
- **설치 상세:** A의 `UNCONFIRMED_LAUNCH` 네이티브 복구와 B의 실제 다운로드·적용 실행 확인·재시작 이벤트를 각각 보관한다.

확인된 정상 설치가 한 개여도 최초 실패 설치의 회복 또는 모든 설치의 정상화를 뜻하지 않는다. 이번 사례의 A는 실패 배포 ID를 네이티브 차단 목록에 유지하고 이전 정상 배포로 돌아갔다. B는 같은 실패 감지 배포를 정상 실행해 별도 성공 보고를 보냈다. 배포 전체 SDK 적용률도 1/2·50%이며 100%로 바꾸지 않는다.

소유자가 명시적으로 허용한 설치만 자동 판단에 참여한다. 허용 목록은 기기 attestation이 아니다. 정책·허용 설치 변경 이후 새로 게시한 배포만 평가하며 앱·플랫폼·채널·Runtime을 분리한다. 이번 검증은 `flora-verification`, 최소 설치 1개·실패율 100%·관찰 기간 30분에서 수행했다. 다른 운영 채널까지 변경했다는 의미는 아니다.

## 취소 스냅샷과 안전한 표시

기존 판단 DTO의 최초 수치·사유·시각을 덮어쓰지 않고 새로 취소한 판단에만 다음 선택적 `cancellation` 스냅샷을 추가한다.

| 필드 | 의미 |
|---|---|
| `checkedAt` | 취소를 결정한 서버 재확인 시각 |
| `attemptedInstallations` | 재확인 시점의 적용 시도 설치 수 |
| `failedInstallations` | 재확인 시점에 실패로 집계되는 설치 수 |
| `confirmedHealthyInstallations` | 실제 정상 실행 확인 보고를 충족한 설치 수 |
| `failureRatePercent` | 재확인 실패율, 표본이 0개인 경우만 `null` |

스냅샷은 `skipped`·`AUTO_ROLLBACK_RECOVERED`인 새 취소 판단에만 표시한다. 정상 확인 수는 현재 실패하지 않은 설치 수를 넘을 수 없다. 잘못된 수치·실패율·시각, 용량 부족이나 정책 변경 중단을 정상 실행 확인으로 표시하지 않는다. 과거 스냅샷 없는 취소 기록에는 기존 일반 안내만 표시하고 수치를 만들어 넣지 않는다.

용량 부족의 `AUTO_ROLLBACK_ACCOUNTING_CAPACITY`는 **집계 용량 부족으로 자동 롤백 중단**, 새 실패의 확인을 다시 기다리는 `AUTO_ROLLBACK_CONFIRMATION_PENDING`은 명시적 지연 표식이 있을 때 **새 실패의 2분 확인 대기**로 구분한다. SDK의 일반 `recoveredInstallations`와 서버의 취소 사유 코드를 같은 의미로 사용하지 않는다.

추가 API나 자동 polling은 없다. 기존 정책·배포 상세 응답에서 스냅샷을 함께 읽으며 기존 캐시·수동 새로고침·페이지당 20개 제한을 유지한다. 최초 판단 수치와 취소 스냅샷은 서버가 보관한 별도의 시점 정보다. 최종 상세 화면에서 **65,001ms 동안 API 요청 0건**을 계측했다.

## 테스트 결과와 첫 실패 기록

최종 전체 직렬 실행은 **1,207건 중 1,204 통과·0 실패·3 선택적 건너뜀**, 439.0초에 종료했다. 이 전체 실행은 로컬 구현·HTTP·SDK·UI 회귀 증거이며 실제 기기 사례는 위 별도 증거로 확인한다. 건너뛴 기존 선택적 테스트는 Windows profile/junction, 실제 Expo CLI export, 실제 PNPM metadata transfer다. opt-in export를 실행하지 않았다는 사실과 EAS·Actions 미사용을 구분한다.

첫 전체 실행은 1,203 통과·1 실패·3 건너뜀이었다. `credential-http.test.ts:98`의 거대한 초과 본문 HTTP 요청이 Worker의 본문을 읽지 않는 조기 413 응답과 경합해 `write EPIPE`로 실패한 증거를 `full-tests.log`에 보존했다. 자격 증명 API 파일만 한 번 실행한 초기 재현에서는 5/5 통과해 재현되지 않았다.

이 테스트 안정화 수정은 테스트와 fixture 두 파일에 한정했다. 기존 아홉 종류의 자격 증명 HTTP 등록·인증 검증은 유지하고, 거대한 읽지 않는 HTTP probe만 작은 test-only 요청으로 만든 workerd 내부 스트림에 바꿨다. 실제 production Worker/auth 경로에서 헤더 초과는 413·본문 읽기 0회, 스트림 초과는 1,500,000바이트 뒤 마지막 한 바이트에서 413·총 1,500,001바이트·24회 pull을 확인했다. 거절 후 자격 증명 DTO도 동일했다. 오류를 무시하거나 변경 요청을 재시도하지 않았고 운영 본문 제한·의존성·제품 코드는 바꾸지 않았다. 이는 통제된 경계 테스트로의 교체이며 운영 네트워크나 provider 장애를 고쳤다는 주장이 아니다.
