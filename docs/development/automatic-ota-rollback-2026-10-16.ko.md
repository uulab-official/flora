# 실패율 기준 자동 OTA 롤백 — 2026-10-16

Flora 관리자에서 앱별 자동 롤백 정책과 판단에 참여할 설치를 관리한다. 기존 서명·이전 배포·자산을 재사용하며 EAS와 GitHub Actions는 사용하지 않는다. 여섯 앱·플랫폼 조합에서 실패 감지부터 자동 롤백 게시·다운로드·적용·재시작 및 관리자 상세 화면까지 확인했다. 이 문서는 기기 실행 증거와 로컬 통합 테스트를 구분한다. 기기 검증은 Isso·Promise·Reward의 기존 Release 앱을 설치한 전용 iOS 시뮬레이터·Android 에뮬레이터 기준이며, 물리 기기 검증을 의미하지 않는다.

## 사용 방법

1. 프로젝트 → **OTA 배포** → **실패율 기준 자동 롤백**을 연다. 기본값은 **꺼짐 · 실패율 10% · 최소 20개 설치 · 게시 후 30분**이다.
2. 사용할 채널과 iOS·Android의 정상 복원 배포를 지정한다. 같은 앱·플랫폼·채널·Runtime에서 정상 적용 및 재시작 보고가 각각 한 건 이상이고 실패·네이티브 롤백 보고가 없는 배포만 사용한다. 현재 정상 배포를 다음 신규 배포의 복원 대상으로 고정할 수 있다.
3. 배포의 **기기별 적용 현황**에서 직접 검증한 설치에 **자동 롤백 판단에 허용**을 누른다. **허용 해제**도 같은 화면에서 처리한다. 일반 익명 SDK 보고는 화면에 계속 집계되지만 자동 롤백 권한에는 사용하지 않는다. 허용 설치가 0개면 정책을 켜도 자동 롤백은 실행되지 않는다.
4. 정책 또는 허용 설치를 변경한 **이후 새로 게시한 배포**부터 평가한다. 변경 이전 배포·과거 보고를 소급 평가하지 않는다. 허용 설치의 변경도 정책 버전을 올리므로 이전 설정 화면은 새로고침한 뒤 저장해야 한다.
5. **자동 롤백 감지·실행 이력**에서 실패 설치 수/적용 시도 설치 수, 설정 버전, 판단 사유와 처리 상태를 확인한다. **실패 감지 배포 → 정상 복원 원본 → 자동 롤백 배포·기기 상세**를 따라 실제 다운로드·적용·재시작 결과를 확인한다.

허용 목록은 소유자가 확인한 설치 식별자에 자동 판단 권한을 주는 방식이다. Apple App Attest·Google Play Integrity 등의 기기 attestation을 수행했다는 뜻은 아니다. 익명 보고가 진짜 설치라는 신뢰 근거가 되지 않으므로 실제 확인한 설치만 허용해야 한다. 원시 설치 UUID와 서버 해시는 UI에 노출하지 않고 앱·배포에 묶인 암호화 참조로 소유자 작업을 수행한다.

## 실패율과 복구의 의미

- 분모는 허용 설치 중 해당 배포의 **적용·실행을 시도했다고 보고한 고유 설치 수**다. 다운로드만 한 설치와 업데이트 확인만 한 설치는 분모에 포함하지 않는다.
- 분자는 적용·실행 단계의 실패 또는 네이티브 자동 복구를 보고한 설치 수다. 검증에서는 실행 확인 전 프로세스를 종료해 실제 네이티브 `UNCONFIRMED_LAUNCH` 복구를 유도했다. 같은 설치가 이벤트를 여러 번 전송해도 한 번만 센다.
- 업데이트 확인·다운로드의 네트워크 실패, `NETWORK_UNAVAILABLE`·`TIMEOUT`은 자동 롤백 임계치에 포함하지 않는다. 일반 실패·복구 상세 이력에는 보존된다.
- 정상 적용되지 않은 문제 배포에서 **적용 미확인·재시작 미확인**을 그대로 표시한다. 서버가 정상 복원 번들을 새 배포로 게시한 후, 새 배포의 실제 SDK 확인을 받아야 **적용 확인·재시작 확인**이 된다.
- SDK의 일반 `failedInstallations`가 0이어도 네이티브 `rolledBackInstallations`가 1이면 자동 판단의 실패 설치는 1이다. 서로 다른 지표를 같은 수치로 바꾸거나 성공으로 덮어쓰지 않는다.
- SDK 보고가 도착할 때만 판단한다. 미보고 크래시나 전체 설치 수를 알고 있다고 표시하지 않는다. QA의 1/1 결과는 허용한 검증 설치 한 건의 증거다.

## 안전 장치와 저장 규칙

정책은 소유자·앱별로 저장하고 iOS·Android·채널·Runtime별로 실행한다. 복원 대상은 실패한 배포보다 오래되어야 하며 실행 직전에도 정상 보고 상태와 현재 최신 배포를 확인한다. 최신 배포가 바뀌면 오래된 판단으로 되돌리지 않는다. 복원 배포 자체에서 다시 자동 롤백을 만들지 않는다.

판단 시 정책과 실패 수를 스냅샷으로 남기고, 원본 배포마다 한 번의 판단과 고정 요청 키를 사용한다. 새 UUID의 롤백 배포가 이전 정상 자산 전체를 재사용하며 문제 배포·복원 원본을 수정하지 않는다. 최신 배포 CAS와 기존 D1 롤백 보호를 통과해야 게시된다. D1 쓰기 응답이 유실되면 같은 요청의 영수증을 먼저 찾아 중복 게시를 막는다. 이미 커밋한 영수증은 정책을 껐더라도 실제 게시 결과로 정리한다.

소유자의 정책 끄기와 허용 해제는 실행 중인 작업의 정책 버전을 무효화할 수 있다. 기존 정책 끄기는 D1 장애 중에도 DO의 CAS로 처리한다. 실행 대기·진행·재시도 의도는 DO에 보존되고 alarm으로 이어지며, 재시작 시 영수증을 확인한다. 선택적 alarm 초기화 실패로 기존 인증·GitHub 연결을 지우지 않는다. 보관 예산이 찼을 때는 추가 허용·집계를 제한하되 기존 허용 해제를 막지 않는다. 상세 이력은 삭제하거나 가상의 이벤트로 보충하지 않는다.

소유자 API는 다음과 같다. 쓰기에는 기존 소유자 세션·Origin·CSRF 검사가 적용된다.

| API | 용도 |
|---|---|
| `GET /api/apps/:appId/ota/rollback-policy` | 정책, 허용 설치 수, 최근 판단 20건과 허용 변경 20건 |
| `POST /api/apps/:appId/ota/rollback-policy` | `expectedVersion`으로 정책 CAS 저장 |

공개 SDK 세션은 보고 범위를 증명할 뿐 자동 배포 권한을 부여하지 않는다. 익명 호출자가 20개 설치 UUID를 만드는 모의 공격은 자동 판단을 만들지 못하는 로컬 통합 테스트로 검증했다. 운영 서비스에 가짜 실패 SDK 이벤트를 주입해 검증한 것은 아니다.

## 조회량과 서비스 반영

새 D1 마이그레이션, export, 자산 업로드, 앱 바이너리 교체를 추가하지 않는다. 정책·고유 설치 집계·허용 변경·판단 의도는 기존 DO에 추가 저장한다. 기존 D1·DO·Vault·Runner 구성을 바꾸지 않고, 복원 배포 게시에는 기존 D1 경로를 사용한다.

정책은 OTA 화면 진입 또는 명시적 새로고침 때만 읽는다. 기기 상세는 기존의 페이지당 20개·60초 캐시·수동 조회를 유지하고 판단 이력을 함께 전달한다. 허용 변경 버튼은 알려진 해당 설치의 권한 표시만 갱신하고 다른 상세 캐시를 무효화한다. 별도 자동 polling, 앱 전체 D1 스캔, SDK 이벤트 조작을 추가하지 않는다. 운영 상세 화면에서 **87,394ms 동안 추가 API 요청 0건**을 확인했다. 진행 중인 영속 판단이 있을 때만 alarm이 실행된다.

Worker `flora-uulab` 버전 `eec5e97c-e19d-48a5-ac9c-0550a8a17b91`이 100% 반영된 상태를 확인했다. 기존 12개 바인딩을 유지했고 D1 마이그레이션은 실행하지 않았다. PC Runner는 전후 같은 서비스 PID `62598`로 실행 중이며 네 구성 파일의 해시가 동일했다.

여섯 조합 모두 판단 스냅샷은 실패 1/1·100%이며, 문제 배포에서는 다운로드 1·적용 0·재시작 0·네이티브 복구 1이다. 복원 배포에서는 다운로드·적용·재시작이 각각 1이고 네이티브 복구·일반 실패는 0이다. 원본 상세 화면에서 **다운로드 확인 / 적용 미확인 / 재시작 미확인**과 실행 확인 실패 원인을, 복원 상세에서 **다운로드 확인 / 적용 확인 / 재시작 확인**을 직접 확인했다.

기본 lifecycle의 업데이트 확인·다운로드·적용 요청·적용 실행 확인·재시작 확인을 상세 이벤트에서 확인했다. 반복 보고나 재시도가 보관된 행은 실제 5건보다 많을 수 있다. 중간 시도가 관찰 기한 내 완료되지 않은 helper 로그도 보존했다. 이 로그를 성공으로 세거나 근거 없이 다운로드 지연·입력 누락 중 하나로 단정하지 않는다.

여섯 조합 모두 native manifest 서명과 다운로드 파일 해시를 확인하고 실제 active 배포 ID·실행 확인 결과를 서버 상세와 대조했다. 검사 파일 수는 Isso iOS 36개·Android 40개, Promise iOS 47개·Android 51개, Reward iOS 53개·Android 57개다. 바이너리와 앱 데이터 sentinel은 모두 보존됐다. 정상 복원 배포가 실제 적용·실행 확인된 이후에는 보고를 보내기 위한 추가 시작 없이 SDK 상세에 반영됐고 outbox가 비워졌다. 이 관찰을 처음 다운로드를 시작한 실행에서 모두 즉시 적용됐다는 의미로 해석하지 않는다. Reward의 기존 8초 시작 정책을 유지했고 캐시를 다음 정상 시작에서 적용하는 준비 단계와 최종 확인 이후 추가 실행 여부를 구분했다.
