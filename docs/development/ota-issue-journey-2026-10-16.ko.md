# OTA 문제 전체 타임라인 검증

검증일: 2026-10-16. 운영 화면: https://flora.uulab.co.kr/projects

## 사용 방법

프로젝트의 OTA 배포 상세에서 익명 설치의 `상세 이벤트 보기`를 열고 `문제 전체 흐름 보기`를 누른다. 원래 문제 배포부터 연결된 정상 롤백, 후속 롤백 재실패, 재복구까지 같은 설치의 실제 보고와 배포 게시 기록을 하나의 시간순 목록으로 표시한다. 각 항목의 배포 상세 링크로 해당 배포에 이동할 수 있다. 복구 배포에서 열어도 검증된 원래 문제까지 연결된다.

처음에는 20개를 표시하고 `이후 기록 더 보기`로 같은 목록에 이어 붙인다. `문제 흐름 새로고침`은 새 기준 시점으로 다시 조회한다. 원래 배포의 개별 이벤트·누적 집계·실패 배지와 상세 링크도 유지한다. 롤백으로 해결되었다고 원래 실패 배포의 적용·재시작 플래그를 성공으로 바꾸지 않는다.

배포 게시는 기기의 다운로드·적용 성공과 별도로 표시한다. 기기 보고 시각과 서버 수신 시각을 구분하며 시계 차이·동시 보고의 순서를 인과관계로 단정하지 않는다. 원래 OTA, 롤백 1·2·3 등 운영용 이름을 사용하고 긴 내부 ID를 본문에 나열하지 않는다.

## 실제 운영 화면 검증

기존 전용 QA iOS Simulator와 Android 에뮬레이터의 실제 Isso·Promise·Reward Release 앱이 보고한 원래 OTA A → 정상 롤백 R1 → 재실패 R2 → 재복구 R3 이력을 사용했다. 네이티브 실행 검증 방법과 배포 ID는 [앞선 롤백 재실패 검증](rollback-relapse-2026-10-16.ko.md)에 있다. 이번 검증은 그 실제 수집 이력을 새 운영 UI에서 대조한 것으로, 새 물리 기기 테스트나 새 실패 주입·네이티브 빌드·OTA 게시는 수행하지 않았다. EAS·GitHub Actions를 사용하지 않았다.

| --- | --- | ---: | ---: | --- |

| Isso | iOS | 27 | 2 | 확인 |

실서비스의 프로젝트 목록에서 여섯 원래 문제 상세로 이동했다. 각 타임라인에서 R2의 `네이티브 자동 롤백 / 실행 확인 실패`와 R3의 다운로드 완료·적용 실행 확인·재시작 확인을 확인했다. 페이지를 이어 붙여도 기존 항목·순서가 보존되고 중복이 없으며 링크는 같은 앱의 해당 배포에 한정된다. Reward Android의 R3 링크로 실제 이동한 뒤 원래 문제부터 다시 연결되는 것도 확인했다.

Isso·Promise Android에는 이전 네이티브 검증에서 R3 실행 중 전송된 추가 R2 롤백 보고도 있다. 이를 새 충돌로 추정하거나 삭제하지 않고 원래 보고 시각으로 표시한다. 390px 모바일에서 가로 넘침·중첩 링크/버튼은 0건이며 실패·재복구 화면도 확인했다.

## 조회량과 안전한 페이지 이동

- 새 자동 조회·타이머·목록별 추가 요청은 없다. 실제 상세 화면 65초 유휴 관찰에서 API 요청은 0건이었다.
- 전체 흐름 버튼을 누르기 전 새 journey 요청은 0건이다. 여섯 흐름은 열기 1회 + 다음 페이지 1회, 각각 총 2회로 조회했다.
- 60초 이내 같은 설치를 다시 열었을 때 추가 journey 요청은 0회, 명시적 새로고침은 1회였다.
- 페이지당 최대 20개, 연결 배포 최대 33개, 원래 계보 최대 32단계다. 기존 인덱스로 같은 앱·플랫폼·채널·런타임 범위를 한 번 읽고 2,001개 게시에서 중단한다. 초과·미기록·레거시·불완전 연결을 명시하며 성공을 추정하지 않는다.
- 수동 페이지당 D1 명령은 2개다. 이는 2행 읽기라는 뜻이 아니다. 최종 2,001개 게시 상한 시험에서 실제 읽기는 6,017행이었다. SDK 보고의 추가 D1 조회 0회와 기존 목록 조회 방식은 유지된다.
- 커서는 소유자·origin·DB·앱·배포·설치·조회 모드와 조회 시점, 수신 행 경계, 연결·이력 정보를 봉인한다. 이후 보고나 새 배포가 이전 페이지에 섞이지 않는다. 이력 분류가 바뀌면 409로 새로고침을 요구하고 화면의 기존 기록을 보존한다.
- 이전 세션의 지연된 401이 새 로그인 세션을 종료하지 않으며, 잘못된 범위·원인 코드·시점의 DTO를 표시하지 않는다. 원본 설치 ID·SDK 티켓을 응답이나 문서에 노출하지 않는다.

SQLite 사용은 [Cloudflare 공식 저장소 문서](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)와 workerd 테스트로 확인했다.

## 데이터 보존·회귀 검사·배포

D1 배포 원문 114건의 소유자·앱·ID·JSON이 배포 전후 모두 동일하고 추가 배포는 0건이다. 여섯 조합의 A·R1·R2·R3, 총 24개 배포에서 조회 시각과 매번 봉인되는 설치 참조를 제외한 원래 플래그·실패 원인·해결 근거·누적 집계·보관 이력이 동일했다. 세 앱의 저장소 연결·설정·소스·키 및 접근 이력·자동 롤백 정책·자동화 정책·작업 이력과 Cloudflare 연결 리소스 12개도 보존됐다. Runner의 실시간 presence 시각·상태 변화는 설정 변경과 구분했다.

관련 backend 95개와 UI 233개, 총 328개 테스트가 모두 통과했다. 타입 검사·호스팅 빌드·diff 검사·배포 dry run과 독립 검토도 통과했다. 범위 격리, 원본 보존, 중간 보고 수신, 새 게시 도착, 커서 오용·권한 해제, 부분 이력·깊이/범위 상한, 캐시·오래된 401을 포함한다.

운영 Worker `d3dbfac4-402e-42db-a1ce-547001b33a9c`에 트래픽 100%가 적용됐다. 인증된 `/projects` HTML, `deployment-devices.js`, `app.css`의 SHA-256이 최종 로컬 빌드와 일치한다. 새 리소스·요금제·마이그레이션은 추가하지 않았다.

별도 운영 관찰: 최종 PC Runner 상태는 `fatal-stop / MANUAL_INSPECTION_REQUIRED`였다. 복구 저널을 보존하는 기존 안전 중지 표식이 있으며 이번 읽기 중심 검증에서는 제거하거나 강제 재시작하지 않았다. 이번 타임라인 확인은 기존 수집 이력의 화면 검증이며 Runner 자동 빌드가 현재 정상 실행 중이라는 근거로 사용하지 않는다.

후속 복구 검증에서는 중지 원인과 용량 문제를 수정하고, Isso·Promise·Reward의 iOS·Android GitHub 자동 OTA 6건을 PC Runner로 게시한 뒤 번들 다운로드까지 확인했다. 당시 중지 표식·로그·복구 디렉터리는 비공개 백업에 보존했다. 최종 상태와 원본 보존 대조는 [PC Runner 복구 기록](runner-resume-2026-10-16.ko.md)에 별도로 기록한다.

비공개 원본 증거는 `dist/ota-issue-journey-2026-10-16/evidence/`, 화면 캡처는 `output/playwright/ota-issue-journey-2026-10-16/`에 보관했다. 주요 증거는 `journeys-live.json`, `ui-live.json`, `cache-refresh.json`, `idle-65s.json`, `mobile.json`, `preservation-final.json`, `active-deployment.json`과 회귀 검사 로그다. 인증 세션·비밀번호·개인키는 증거에 저장하지 않았다.
