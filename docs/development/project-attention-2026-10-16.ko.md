# 프로젝트의 문제 보고 찾기와 OTA 기기 이력 바로가기 — 2026-10-16

프로젝트 목록에서 저장소·앱 검색과 상태 필터를 함께 사용하고, 문제 보고가 있는 iOS·Android 배포 및 해당 설치의 이벤트로 바로 이동할 수 있게 했다. 기존 `/api/projects` 응답을 재사용하며 목록 필터나 검색 때문에 앱별 운영 API를 추가 호출하지 않는다.

## 사용 방법과 집계 범위

1. [프로젝트 목록](https://flora.uulab.co.kr/projects)의 **운영 상태**에서 **확인 필요**를 선택한다. 앱 이름·저장소·배포 채널 검색과 함께 적용된다.
2. **OTA 실패·복구 보고**, **Runner 확인 필요**, **상태 미확인**으로 더 좁힐 수 있다. 전체 프로젝트 수와 조건에 맞는 수를 구분해서 표시한다.
3. 각 앱의 **iOS/Android 문제 배포**는 기존 배포별 전체 현황으로 이동한다. **iOS/Android 실패 기기 이력**은 실패·네이티브 복구 설치만 보여주고 첫 설치의 이벤트를 한 번 연다.
4. 목록으로 돌아오면 같은 세션의 검색과 상태 조건을 유지한다. 로그아웃하면 검색과 비공개 화면을 지우고 필터를 초기화한다.

프로젝트 목록의 OTA 기준은 각 플랫폼의 **최근 배포**다. 일반 실패 또는 네이티브 자동 복구 보고, 실패 원인이 있으면 표시하며 복구된 누적 이력도 포함한다. 현재 미복구 장애 수라고 해석하지 않는다. 실패·롤백·복구 수치는 중복될 수 있어 빼거나 더해 미해결 수를 만들어내지 않는다. 더 오래된 배포는 앱의 OTA 배포 이력에서 확인한다.

Runner는 자동 배포 정책이 켜져 있을 때 오프라인·미등록·연결 이력 없음·권한 폐기를 확인 대상으로 표시한다. 오래되거나 불러오지 못한 상태는 오프라인으로 단정하지 않고 미확인으로 분리한다. 유효하지 않거나 다른 앱·플랫폼의 배포 정보로는 바로가기를 만들지 않는다.

## 기기 조회와 보존

새 정식 경로는 `/apps/{appId}/ota/{deploymentId}/issues`다. 로그인 후에도 이 경로로 돌아올 수 있다. 서버의 `GET .../telemetry?filter=issues`는 `failed=1 OR rolledBack=1`인 설치 이력을 페이지당 최대 20개 반환한다. 복구된 기록을 제외하거나 원래 실패 기록을 지우지 않는다. SDK 누적 현황의 숫자는 계속 **전체 배포** 기준이며, 필터로 보이는 설치 수와 구분한다.

- 목록 조건 변경·검색: 추가 API 조회 **0회**.
- 문제 기기 진입: 설치 목록 **1회**, 첫 설치 이벤트 **1회**. 앱 선택이 바뀌면 기존 앱 상태 조회도 수행한다. 앱별 전체 운영 정보나 모든 설치를 미리 읽지 않는다.
- 이후 페이지 이동·수동 새로고침: 첫 설치의 이벤트를 다시 자동 조회하지 않는다. 기본 전체 설치 화면의 이벤트는 기존처럼 클릭할 때만 조회한다.
- 목록·이벤트 페이지는 기존 60초 캐시와 20개 제한을 유지하며 새 폴링이나 타이머는 추가하지 않았다.
- 문제 목록과 전체 목록의 커서는 서로 다른 범위로 봉인한다. 다른 앱·배포·필터의 커서는 D1 조회 전에 거절한다. 이벤트 커서도 앱·배포·설치별로 분리한다.
- 기존 DO에 문제 이력용 부분 인덱스만 추가했다. 첫 인덱스 생성·관련 보고 갱신에는 인덱스 쓰기가 발생한다. D1 마이그레이션·새 리소스·기존 보고 재작성은 없다. 인덱스 검색과 페이지당 D1 확인 2회를 통합 테스트로 검증했다.

리뷰에서 이전 이벤트 페이지 커서가 다른 앱·배포의 첫 자동 상세 조회에 남는 문제도 재현해 수정했다. 화면 진입·종료·초기화·첫 설치 선택 시 이벤트 페이지 기록을 초기화하며 세 전환 방식의 회귀 테스트를 추가했다.
