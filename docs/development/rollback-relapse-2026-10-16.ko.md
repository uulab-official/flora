# 롤백 재실패와 재복구 검증

검증일: 2026-10-16. 운영 화면: https://flora.uulab.co.kr/projects

후속 화면 검증: [원래 OTA부터 롤백·재실패·재복구까지 한 타임라인](ota-issue-journey-2026-10-16.ko.md).

## 상태 전환

같은 설치에서 정상 롤백의 적용·재시작을 확인해 해결한 문제라도, 연결된 후속 롤백에서 실패가 발생하면 원래 문제를 다시 `미복구`로 표시한다. 이후 최신 실패보다 나중인 정상 적용 실행과 재시작을 모두 확인해야 다시 `롤백으로 해결됨`이 된다.

원래 문제 상세에는 재실패 시각·원인과 `실패한 롤백 배포 이력` 링크를 제공한다. 재복구 후에도 이 원인 기록은 유지하고, 새 적용·재시작 시각과 `정상 복구된 롤백 배포 이력` 링크를 함께 표시한다. 원래 실패 배포의 적용·재시작 미확인 표시나 누적 통계를 성공으로 바꾸지 않는다.

## 실제 게시 순서에 맞춘 롤백 계보

기존 구현은 한 단계의 연결만 처리했다. 실제 게시 API는 현재 최신 배포에서만 롤백하도록 검사하므로 다음 흐름을 처리해야 한다.

```
원래 문제 A → 정상 롤백 R1 → 실패한 후속 롤백 R2 → 정상 재복구 R3
```

각 연결에서 D1 원본의 소유자·앱·플랫폼·채널·런타임, 정상 복원 원본의 존재, 게시 순서를 다시 검증한다. 클라이언트가 제공한 계보나 롤백 여부만으로 원래 문제를 연결하지 않는다. 검증된 체인만 서버 내부 같은 설치 식별값으로 연결한다.

허용 깊이는 32단계다. 중간 연결의 범위·순서가 잘못됐거나 체인이 불완전하거나 깊이를 초과하면 성공을 추정하지 않는다. 프로젝트는 명시적인 상태 미확인을 유지하며 이전 성공 근거도 보수적으로 무효화한다. 원래 문제 상세의 `rollbackFailure`는 현재 페이지의 설치에 한정해 최신 관련 실패를 조회하는 파생 정보다.

새 실패가 발생하면 오래된 적용·재시작 보고로 문제를 해결할 수 없다. 다른 설치의 보고, 게시·세션 발급·다운로드만의 성공, 한쪽 확인만 도착한 경우, 같은 시각 또는 순서가 바뀐 재전송도 해결 근거가 되지 않는다. 보고 저장과 파생 집계 갱신은 한 트랜잭션으로 처리한다.

## 네이티브 검증 방법

기존 전용 QA iOS Simulator와 Android 에뮬레이터의 실제 Isso·Promise·Reward Release 설치를 사용했다. 물리 기기·스토어 출시 검증은 아니다. EAS·Actions를 사용하지 않았으며 앱 바이너리 재빌드·재설치도 하지 않았다.

이미 정상 확인된 R1은 네이티브 엔진이 다시 적용하지 않으므로, 새 R2와 R3 ID를 게시했다. 기존 정상 배포의 서명·자산을 재사용해 총 12건을 추가했다.

R2가 실제 네이티브 적용 대기 상태에 들어간 순간, 기존 QA 도구가 전용 설치의 정확한 프로세스만 중단했다. 다음 실행에서 네이티브 엔진이 R2를 차단하고 R1으로 복귀했으며 SDK가 `rolled_back / launch / UNCONFIRMED_LAUNCH`를 보고했다. 네이티브 상태 JSON, SDK 보고, 차단 목록은 수동 수정하지 않았다. 기존 차단 ID 세 개는 모두 유지하고 엔진이 실패한 R2 한 개를 추가했다.

서버 보강 배포 후 이미 수신된 실제 R2 보고만으로 원래 A 여섯 건이 미복구로 돌아가는 것을 확인했다. Flora 실제 목록에서 미복구 앱 3개와 여섯 원래 문제의 진입 링크를 확인하고, 각각 원래 문제 → 실패한 R2 → 네이티브 실패 이벤트까지 열어 캡처했다.

R3 게시 직후에는 여섯 A가 계속 미복구인 것을 확인했다. 이후 실제 앱에서 R3를 다운로드·적용하고, 정상 실행과 프로세스 재시작을 확인했다.

여섯 R3의 SDK 집계는 각각 다운로드 1, 적용 실행 1, 재시작 1이다. 여섯 A는 각각 미복구 0, 해결됨 1, 롤백으로 해결됨 1이다. 각 A의 실패 설치는 여전히 원래 배포의 적용·재시작 미확인을 유지한다. R2의 원래 실패 이벤트는 모두 남아 있고 R2 자체도 R3로 해결된 상태다.

실서비스 브라우저에서 여섯 A의 재해결 화면을 열어 R2 실패 링크, R3 복구 링크와 두 시점을 확인했다. R3 상세에서도 다운로드·적용·재시작 세 단계를 확인했다. 최종 목록은 미복구 앱 0개, 해결됨 앱 3개다. 390px 모바일 화면에 가로 넘침이나 중첩 링크·버튼이 없었다.

Reward의 기존 시작 시간 제한은 유지했다. 다운로드가 끝난 캐시를 정상 후속 실행에서 적용했으며, 최초 다운로드 실행에서 즉시 적용됐다고 주장하지 않는다.

## 기존 데이터 보존

- D1 기존 배포 102건의 소유자·앱·ID·원문 JSON을 전부 대조했다. 기존 행은 동일하고 예상한 R2·R3 12건만 추가되어 총 114건이다.
- 세 앱의 저장소 연결, 탐지 기록, 기존 자산, 자동 롤백 정책·이력, 인증서·키와 접근 이력, 자동화 정책·작업, 앱 설정, 소스 스냅샷·이력이 동일하다.
- 원래 A의 원시 SDK 플래그·누적 통계·보고 이력은 파생 상태 필드를 제외하고 동일하다. R2의 최초 실패 이벤트도 각각 원래 시각으로 조회된다.
- Isso·Promise Android에서는 실제 후속 실행 과정에서 SDK 이벤트가 한 건씩 추가됐다. 기존 이벤트를 덮어쓰지 않았고 실패 설치 누적 수는 그대로다. 보고 시각과 이벤트 수의 정상 증가를 데이터 훼손으로 취급하지 않고, 원래 이벤트 보존과 누적 플래그를 별도로 대조했다.
- 여섯 설치의 실행 바이너리·내장 번들 또는 APK와 데이터 표식 해시는 동일하다. 최종 SDK 보고 대기열은 모두 0건이다.
- Cloudflare 기존 12개 연결 리소스가 동일하며 새 유료 리소스·요금제 변경은 없다. PC Runner 서비스도 기존 상태로 실행 중이다.

## 조회량과 회귀 검사

SDK 보고·중복 수신은 D1 추가 조회 0회다. 배포 상세는 기존 두 번, 프로젝트 기본 투영은 기존 세 번의 D1 명령을 유지한다. 목록은 최신 배포와 검증된 원래 문제만 집계해 최대 400개 대상의 기존 상한을 유지한다. 상세 실패 원인은 현재 최대 20개 설치 페이지의 DO 인덱스 조회로 구하며 기기별 D1 요청을 추가하지 않는다.

기존 계보와 파생 상태는 한 번만 보정한다. 같은 이력 워터마크에서는 계보 재조회가 없다. 프런트엔드 API·타이머·폴링은 추가하지 않았다. 실제 목록 검색·필터 변경은 API 호출 0회, 최종 원래 문제 상세의 65초 유휴 관찰도 API 호출 0회였다. 기존 프로젝트 목록의 주기적 갱신은 유지한다.

관련 12개 테스트 파일의 통합 실행 284건이 전부 통과했다. 최종 목록 투영 5건과 테스트 타입 수정 후 프로젝트 UI 55건도 별도 통과했다. 독립 검토는 깊이 초과, 중간 범위 오류, 부분·재전송 보고, 마이그레이션·트랜잭션 원자성 등을 재검증했고 지적한 잘못된 최초 계보의 미확인 처리도 수정·재검증했다. 최종 hosted build, 전체 타입 검사, `git diff --check`, 배포 dry run이 통과했다. 이번에는 전체 저장소의 21분 테스트를 반복하지 않았다.

운영 Worker 버전은 `8f1631b4-3638-4a42-8ba7-0e43eb7bd746`, 트래픽 100%다. 운영 HTML과 변경 JS 두 개의 해시가 최종 빌드와 일치한다. SQLite 트랜잭션·동기 커서 사용은 [Cloudflare 공식 저장소 문서](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)와 프로젝트 workerd 테스트를 기준으로 확인했다.

비공개 원본 증거: `dist/rollback-relapse-2026-10-16/evidence/`. 실제 UI 캡처: `output/playwright/rollback-relapse-2026-10-16/`. 주요 파일은 `native-fault-sdk-reports.json`, `original-reopened-reports.json`, `projects-recovery-published-only.json`, `final-device-reports.json`, `ui-failed.json`, `ui-recovered.json`, `preservation-check.json`, `regression-tests.log`, `typecheck-final.log`다. 인증 세션·개인키·SDK 티켓은 문서에 포함하지 않는다.
