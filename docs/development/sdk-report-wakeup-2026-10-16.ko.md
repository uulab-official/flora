# 추가 실행 없는 SDK 보고·재전송 검증

2026-10-15~16, Isso·Promise·Reward의 기존 Release 앱과 `flora-verification` 채널에서 검증했습니다.
기존 PC Runner와 Flora를 사용했고 EAS·GitHub Actions·새 바이너리 빌드·재설치는 사용하지 않았습니다.
물리 기기 검증이 아닌 기존 전용 iOS 시뮬레이터·Android 에뮬레이터 검증입니다.

## 수정한 보고 경계

기존 SDK는 전송 중 들어온 요청이 마지막 4번째 배치나 Promise 완료 직전 경계에 도착하면
후속 처리를 놓칠 수 있었습니다. 일시적인 전송 실패에 backoff만 설정하고 같은 실행 내의
재전송을 예약하지 않는 경로도 있었습니다. 앞선 Isso의 대기열 1건만으로 당시 원인을 하나로
단정하지 않고, 이 세 가지 경계를 결정적으로 실패하는 회귀 테스트로 재현한 뒤 수정했습니다.

- 전송 중·최종 확인 응답 뒤·완료 직전 요청을 합쳐 후속 처리에 넘깁니다. 각 요청 처리의
  최대 4개 배치·요청당 16개 이벤트 제한을 유지하며 현재 실행의 배포를 우선합니다.
- 일시적 네트워크 실패·timeout·408·429·5xx는 기존 60초·120초 backoff 후 같은 실행에서
  최대 두 번 자동 재시도합니다. 대기 타이머는 하나이고 빈 큐에서는 조회·전송하지 않습니다.
  새 이벤트가 제한된 재시도 예산을 다시 열어도 backoff를 건너뛰지 않습니다.
- 인증·응답 검증 오류·저장소 장애는 자동 반복하지 않습니다. 기본 저장소 제한 시간은
  1초이고 명시적 상한만 5초로 늘렸으며, 세 앱의 파일 저장소 호스트에 5초를 설정했습니다.
  제한 시간이 끝나도 기존 영속 값은 보존하고 임시 설치 식별자로 보고하지 않습니다.

SDK의 설치 식별자·큐·티켓 프로토콜과 서버 API는 유지합니다. 자동 재시도는 SDK 보고 전송에만
적용되며 업데이트 선택·서명 검증·네이티브 실행 승인·사용자 세션 재시작을 대신하지 않습니다.

다운로드 준비를 위한 시작과 적용 후 보고용 실행을 혼동하지 않습니다.

읽기 전용 observer는 앱 제어·SDK 이벤트 POST를 하지 않습니다. 네이티브 상태·실제 영속 큐·
Android 실행 로그 또는 iOS JS 평가 로그·정확한 배포 상세 API를 대조하고, 확인 뒤 추가 PID·
JS 실행이 없음을 검사했습니다. 각 배포에서 실제 `update_seen`, `downloaded`,
`activation_requested`, `launch_confirmed`, `restart_confirmed` 이벤트가 확인됐습니다.
Isso·Promise는 5개, Reward는 준비와 캐시 재사용의 실제 보고를 포함해 7개가 보관됐습니다.

인증된 Flora 관리자 화면에서도 여섯 배포를 각각 열어 다운로드·적용·재시작과 완전한 새
타임라인을 확인했습니다. 기존 과거 기록의 미수집 시각을 새로 만들거나 채우지 않았습니다.

## Isso의 별도 동일 프로세스 재전송 회귀 검증

첫 OTA 적용 증거를 확보한 **뒤에** 별도 정상 cold start를 한 번 진행했습니다.
전용 QA AVD의 Isso UID에만 HTTPS 차단 규칙을 잠깐 적용했습니다. 실제 실행 확인 보고가
큐에 남고 네트워크 차단 패킷 12개가 발생한 것을 확인한 뒤 규칙을 원복했습니다.

PID `22376`을 유지한 채 통신 복구 후 55,932ms에 보고가 자동 전송됐습니다.
기존 60초 backoff를 지켰고, 큐 0·설치 식별자 보존·서버의 새 실행 확인 이벤트를 확인했습니다.
보고를 보내기 위해 앱을 다시 열거나 `flush()`를 외부에서 호출하지 않았습니다.
최종 네트워크 규칙도 없음을 확인했습니다. 이는 보고 전송 실패 시험이며 OTA 다운로드 실패
이벤트를 임의로 만들어 설치 실패·복구 집계를 늘리지 않습니다.
