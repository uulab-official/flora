# 소규모 표본 자동 롤백 보호 — 2026-10-16

기존 자동 롤백의 정책 필드와 앱별 허용 설치를 유지하면서, 최소 표본을 1~4개로 설정할 때 더 엄격한 네이티브 실행 실패 보호 규칙을 적용한다. 적은 설치만 있는 앱에서도 사용할 수 있게 하되 일시적인 네트워크 실패나 단순 보고 재전송이 즉시 롤백으로 이어지지 않도록 한다.

Flora 운영 서비스에 반영했고 Isso·Promise·Reward의 iOS·Android 여섯 조합에서 네이티브 실행 실패 보고, 서버의 2분 확인, 자동 복원 배포, 다운로드·적용·재시작과 관리자 상세 화면을 확인했다. 환경은 기존 Release 앱이 설치된 전용 iOS 시뮬레이터·Android 에뮬레이터이며 물리 기기 증거가 아니다. 이번 증거는 [이전 자동 롤백 검증](automatic-ota-rollback-2026-10-16.ko.md)과 별도 보관한다. 정상 보고에 의한 취소 등 부정 경로의 로컬 테스트를 실제 기기 취소 검증으로 표현하지 않는다.

## 설정 방법

프로젝트 → **OTA 배포** → **실패율 기준 자동 롤백**에서 **소규모 앱 보호 기준 사용 · 1개·100%**를 누른다. 이 버튼은 입력값만 바꾸며, **자동 롤백 설정 저장**을 눌러야 반영된다. 기존 채널·관찰 기간·정상 복원 대상은 유지된다. 직접 입력할 때도 최소 설치 1~4개로 켠 상태를 저장하려면 실패율 100%를 사용해야 한다. 최소 설치 1개·실패율 10%처럼 안전 규칙에 맞지 않는 조합은 저장 요청 전에 막고 입력값을 보존한다. 이전에 저장한 소규모·낮은 실패율 정책은 경고와 함께 읽을 수 있고, 긴급히 끄는 저장은 실패율을 바꾸지 않고 허용한다.

새 앱의 기본값은 기존과 같이 꺼짐·최소 설치 20개·실패율 10%·게시 후 30분이다. 소규모 모드는 기존 `minInstallations`와 `failureRatePercent`로 결정하며 별도 설정 필드나 새 API를 추가하지 않는다. 정상 복원 배포는 같은 앱·플랫폼·채널·Runtime에서 기존 정상 보고 조건을 충족해야 한다.

허용 설치 수는 **앱 전체 합계이며 플랫폼별 표본이 아니다.** 앱에 허용 설치가 두 개여도 iOS 한 개·Android 한 개라면 각 플랫폼의 표본은 한 개다. 플랫폼별 최소 표본과 실패율을 각각 충족해야 한다. 최소 표본 20을 유지하면 이 두 검증 설치만으로 자동 롤백을 실행할 수 없다.

소유자가 직접 확인해 허용한 설치만 자동 판단에 참여한다. 익명 SDK 보고는 계속 적용 현황에 표시하지만 판단 권한이 생기지는 않는다. 허용 목록은 기기 attestation을 뜻하지 않는다. 정책이나 허용 설치를 변경하면 변경 이후 새로 게시한 배포부터 평가하며 기존 배포·이력은 보존한다.

## 소규모 모드의 판단 규칙

| 보고 | 자동 롤백 판단 |
|---|---|
| 허용 설치의 `activation_requested` 이후, 같은 배포에서 네이티브 `rolled_back`·`stage=launch`·`code=UNCONFIRMED_LAUNCH` 보고 | 고유 설치의 적격 실패로 평가 |
| 일반 적용·실행 `failed`, 다른 단계·사유의 복구 보고 | 소규모 모드의 실패 트리거로 사용하지 않음 |
| 업데이트 확인·다운로드·네트워크 실패 | 실패 트리거로 사용하지 않음 |
| 동일 설치·동일 보고의 중복 또는 재전송 | 표본·실패를 추가로 늘리지 않음 |
| 같은 배포의 정상 `launch_confirmed` 또는 `restart_confirmed` 보고 | 복구 확인 대기 중 자동 롤백 취소 |

최소 표본과 100% 실패율에 도달하면 즉시 게시하지 않고 **2분 복구 확인 대기**에 들어간다. 확인 시점에도 실패 기준이 유지되어야 실행한다. 같은 배포에서 정상 실행 확인이나 재시작 확인이 보고되거나 추가 설치의 보고로 실패율 기준이 충족되지 않으면 `AUTO_ROLLBACK_RECOVERED`로 취소하고 판단 이력을 남긴다. 예를 들어 실패 1/1 뒤 추가 설치가 적용을 요청하면 1/2가 되어 100% 기준에서 벗어날 수 있다. 이 취소만으로 정상 적용·재시작이 확인됐다는 뜻은 아니다. 표본이 작으므로 허용한 설치 한 개의 실제 실행 중단도 큰 비중을 차지한다는 점은 그대로다.

배포별 한 번의 판단·고정 요청 키, 최신 배포 CAS, 정책 변경과 허용 해제에 대한 실행 차단, D1 쓰기 응답 유실 후 영수증 대조, 롤백 배포의 재귀 롤백 금지는 기존 보호 규칙을 유지한다. 이전에 저장한 정책 스냅샷·판단·SDK 보고를 새 규칙의 결과로 재작성하지 않는다.

## 관리자 표시와 조회량

소규모 정책 스냅샷과 명시적 `confirmationDelaySeconds: 120` 표시가 있는 대기 판단에만 **2분 복구 확인 대기**와 서버가 제공한 `nextAttemptAt`의 **확인 예정 시각(KST)**을 표시한다. 취소된 판단에는 **실패 기준 미충족으로 자동 롤백 취소**와 결과 코드를 표시하며 개별 설치의 정상 적용을 추정하지 않는다. 실행 도중 회복 후 새 실패로 확인 시간이 다시 필요한 `AUTO_ROLLBACK_CONFIRMATION_PENDING`은 **새 실패의 2분 확인 대기**로 표시한다. 이는 게시 완료나 일반 실행 실패가 아니며 새 확인 예정 시각에 기준을 다시 검사한다. 과거 최소 설치 1개·실패율 10% 정책으로 생성한 이력은 보존해 표시한다. 과거 1개·100% 판단도 확인 지연 표시가 없다면 새 2분 규칙이 적용됐다고 표시하지 않는다.

별도 카운트다운 타이머나 새 자동 API polling은 추가하지 않는다. 정책 화면 진입 또는 명시적 새로고침으로 상태를 확인한다. 기존 앱·페이지·세션 응답 차단과 CAS 충돌 시 입력 보존을 유지한다. 새 API·export·EAS·GitHub Actions를 사용하지 않으며 기존 배포·키·앱 데이터 삭제를 요구하지 않는다.

새 보고를 온전히 집계할 수 없는 소스는 `AUTO_ROLLBACK_ACCOUNTING_CAPACITY`로 게시를 중단한다. 화면에는 **집계 용량 부족으로 자동 롤백 중단**과 기존 이력 보존 안내를 표시한다. 이를 정상 실행으로 회복했거나 실패율이 낮아졌다는 결과로 해석하지 않는다.

### 관찰 도구의 실패와 별도 확인

Isso iOS의 엄격한 즉시 보고 관찰기는 준비 단계까지 포함한 JS 평가 두 번을 세어 허용치 한 번을 넘었다는 `ADDITIONAL_JS_EVALUATION_OBSERVED`로 실패했다. 이 실패 로그를 보존했다. 별도 읽기 전용 네이티브 프로세스·OS 로그·SDK journal 대조에서는 적용 전 기존 번들 준비 한 번과 목표 번들 평가 한 번을 구분했고, 실행 확인 후 추가 JS 평가 0회, 보고 이후 같은 PID `33316` 유지, 실제 서버 다운로드·적용·재시작 1/1/1을 확인했다.

나머지 다섯 조합은 해당 관찰기가 성공 종료했다. 따라서 엄격한 관찰 도구가 6/6 통과했다고 주장하지 않는다. 여섯 조합의 서명·네이티브 적용·SDK 확인 성공은 그 도구 하나의 성공 여부와 별도의 증거로 확인했다. 초기 관찰 기한 초과와 준비 시도의 로그도 삭제하지 않았으며, 모든 시작 시도에서 처음부터 즉시 적용됐다고 표현하지 않는다. 적용·실행 확인 이후 보고만을 위한 추가 실행이 없었는지와 다운로드·캐시 준비 단계를 구분한다.

## Android 시계 오차 보강

Promise Android 검증 중 호스트 중간 측정값보다 기기 시계가 **33.234초 느린 상태**를 확인했다. 실제 SDK의 첫 세 이벤트가 게시 시각보다 앞선 `observedAt`을 가져 보고 API가 400을 반환했다. 원본 기록에서 업데이트 확인은 게시 시각보다 29.255초, 다운로드는 3.397초, 적용 요청은 3.391초 앞섰다. 원인을 추측해 기기 시각을 바꾸지 않았다.

SDK와 서버 집계의 두 경로에서 게시 시각 기준 과거 허용 범위를 **120초 이내**로 제한해 정상 시계 오차를 수용하도록 보강했다. 원래 `observedAt`과 서버 `receivedAt`은 그대로 보존하며 임의의 정상 시각으로 고치지 않는다. 복구 후 원본 시각 네 건이 상세 journal에 동일하게 남았음을 확인했다. 2분 확인 대기는 이 과거 기기 시각에서 앞당겨 계산하지 않고 서버의 수신·판단 시각부터 유지한다. 기존 미래 시각 120초 제한, 7일 보고 유효 기간, 소유자·앱·배포별 인증 범위는 유지했다. 이 보강 때문에 추가 조회를 만들지 않았다.

## 테스트 결과와 증거 범위

최종 focused 테스트 **100건**, QA helper 테스트 **21건**, typecheck 및 build가 통과했다.
