# SDK OTA 결과 수집과 실제 앱 검증

## 수집 의미

SDK는 앱·플랫폼·Runtime·채널·배포에 묶인 익명 설치 식별자로 확인, 다운로드, 활성화 요청, 실행 확인, 재시작, 실패, 롤백을 보고한다. 원문 오류, 스택, 계정, 하드웨어 식별자는 보내지 않는다. 티켓과 설치 식별자는 앱의 비공개 저장소에만 보관하며 검증 결과에도 기록하지 않는다.

적용은 실제 앱 진입 후 네이티브 `markLaunchSuccessful`이 성공해야 인정한다. 재시작은 이전 JS 실행에 저장한 다운로드 또는 활성화 근거와 새 실행의 네이티브 확인을 함께 요구한다. `reload()` 반환은 적용 근거가 아니다. 적용률의 분모는 해당 배포를 보고한 설치 수다. 전체 사용자 수나 현재 활성 버전 점유율을 뜻하지 않는다.

실패는 단계와 허용된 13개 코드로 집계한다. 같은 설치·배포에서 실패/롤백보다 늦은 적용 및 재시작 확인이 있으면 `recoveredInstallations`를 증가시킨다. 보고 도착 순서가 뒤바뀌어도 중복 집계하지 않는다. 기존 기록에 시각 근거가 없으면 복구를 추정하지 않는다.

## 비용과 보존

- 보고별 D1 조회·쓰기 0회. 티켓 발급 때만 기존 앱·배포를 인덱스로 확인한다.
- 기존 Durable Object에 원자적 중복 제거와 누적 집계, 실패 분류를 저장한다. 최근 플랫폼별 대상에 대해 인덱스 조인 두 번으로 요약한다.
- 관리자 기존 60초 요약 캐시와 숨겨진 화면의 조회 중단을 유지한다. SDK에는 주기적 조회 타이머가 없다.
- 설치의 대기열은 64개 이벤트로 제한하고 7일을 넘은 보고를 정리한다. 실패 시 최소 60초부터 간격을 늘리며 이후 앱 활동/명시적 flush에서 재시도한다.
- 일일 세션 발급 1,000회, 보고 요청 1,000회, 이벤트 5,000개를 제한한다. 누적 설치/배포 조합 20,000개와 배포 2,000개를 넘으면 기존 이력을 보존하고 신규 보고에 429를 반환한다. 무제한 서비스라고 표시하지 않는다.
- 기존 D1 행이나 키를 삭제하지 않는다. 0008은 Isso의 기존 자산이 64MiB에 근접해 앱별 상한만 96MiB로 조정한다. 전체 256MiB, 앱별 자산 128개와 단일 자산 16MiB 제한은 유지한다. 로컬 SQLite의 기존 상한은 변경하지 않는다.

## 검증 출처

기존 앱의 원본 체크아웃 대신 이미 연결된 GitHub QA 브랜치를 사용한다. Isso/Promise는 `codex/flora-ota-integration`, Reward는 `codex/flora-reward-integration`이다. 세 커밋은 PC Runner가 각각 iOS·Android를 export한다. EAS·Actions를 실행하지 않는다. 기존 네이티브 입력 20개를 바이트 그대로 보존한 JS SDK 오버레이를 사용하며 네이티브 버전/Runtime/서명 키를 바꾸지 않는다.

SDK가 없는 기존 번들은 자기 자신의 다운로드를 보고할 수 없다. 따라서 첫 SDK 설치 배포 후 같은 검증된 Runner 자산·커밋을 새로운 배포 ID로 다시 게시해 SDK의 다운로드→적용→재시작을 확인한다. 후속 배포는 운영자가 수행하는 동일 자산 재게시이며 새 GitHub export라고 주장하지 않는다.

기기 검증 범위는 기존 Android QA 에뮬레이터 `Flora_RealApps_Android_OTA_QA_API36`과 iOS QA 시뮬레이터 `Flora Native OTA QA`다. 물리 기기 검증으로 표시하지 않는다. SDK가 환경을 판별하지 못하면 `unknown`으로 보고하며 검증 도구의 환경과 별개로 보존한다.

결과 증거는 `dist/sdk-telemetry-2026-10-15/evidence/`에 저장한다. 네트워크 실패 검증은 해당 QA 앱 UID의 HTTPS만 일시 거절하고 반드시 원상 복구한다. 실패 전후 native 상태, SDK 실패 보고, 재시도 후 새 배포 실행, 프로세스 PID 변경, 서버 집계와 화면을 대조한다.

## 확인 결과 (2026-10-15)

SDK/HTTP/집계/화면을 Cloudflare Worker `7a36fcad-cb6d-48ee-a8c8-13d0d95fe5ac`에 배포했다. 세 앱 모두 PC Runner 온라인이며 다음은 실제 QA 앱의 SDK 보고를 소유자 API와 배포된 화면에서 대조한 결과다. 각 칸은 다운로드 / 적용 / 재시작 설치 수다.

| 앱 | iOS 시뮬레이터 | Android 에뮬레이터 | Android 실패 / 복구 설치 수 |
| --- | --- | --- | --- |
| Isso (있소) | 1 / 1 / 1 | 1 / 1 / 1 | 1 / 1 |
| Promise (우리만나) | 1 / 1 / 1 | 1 / 1 / 1 | 1 / 1 |
| Reward | 1 / 1 / 1 | 1 / 1 / 1 | 1 / 1 |

Android 세 앱 각각 다운로드 중 앱 UID의 HTTPS를 거절해 실제 SDK 실패를 남겼다. 차단을 해제하고 정상 OTA 흐름으로 재시도한 뒤 새 번들 실행, 프로세스 PID 변경, 네이티브 실행 확인 및 서버 복구 집계를 확인했다. 실패 이력은 지우지 않았다. 최종 OUTPUT 규칙에 검증용 차단 규칙이 없음을 확인했다. iOS에는 네트워크 실패를 주입하지 않았다.

Isso·Promise는 실패 사유를 `NATIVE_OPERATION_FAILED`로 보고했다. 네이티브 스트리밍 오류가 일반 오류로 전달되므로 화면에도 ‘네이티브 엔진 작업 실패’로 표시하며 네트워크 오류라고 추정해 바꾸지 않는다. Reward에는 `NETWORK_UNAVAILABLE`와 `NATIVE_OPERATION_FAILED` 두 분류가 남았다. 두 분류가 있어도 실패 설치 수는 중복 제거되어 1이다.

프로젝트 목록은 여섯 플랫폼의 누적 적용률 100%, Android별 실패 1·복구 1, Runner 온라인을 표시했다. Reward 상세에서는 두 실패 원인과 복구 1을 함께 확인했다. 1280px 및 390px에서 가로 넘침이 없었다. `flora-three-apps-recovery-{desktop,mobile}.png`와 `flora-reward-failure-recovery-{detail,mobile}.png`가 화면 증거다. 물리 기기에서는 검증하지 않았다.

### 데이터와 비용 보존

`live-before.json`과 `live-after.json`을 비교해 기존 배포 24개, 자산, 자동화 작업, GitHub 연결, 자동화 정책, 인증서·키 및 접근·교체 이력이 그대로인 것을 확인했다. 새 배포만 추가되어 Isso 9→13, Promise 9→13, Reward 6→10이다. 세 앱의 Android APK SHA-256과 기존 보존 표식, iOS 실행 파일·기본 번들·보존 표식도 동일하다. 매니페스트 서명과 전체 다운로드 자산 해시를 검증했다. 결과는 `preservation-summary.json`, 플랫폼별 `*-restart.json`, `operator-proofs.json`에 있다.

보고 경로의 D1 0회, 관리자 60초 캐시, PC Runner의 사용량 10분 캐시를 유지했다. 화면에서 확인한 2026-10-15 04:11 UTC 계정 전체 사용량은 읽기 595,758 / 5,000,000 (11.9%), 쓰기 26,049 / 100,000 (26.0%)이다. Flora 외 같은 계정의 D1도 포함하며 이후 사용량을 보장하는 값이 아니다. 유료 플랜 변경, EAS, 이 커밋들의 Actions 실행은 없었다.

### 코드 검증과 알려진 경계

전체 직렬 검사 1,058건 중 1,054 통과·3 생략·1 실패였다. 실패는 권한 거절 POST를 연속하는 테스트의 Miniflare 로컬 연결 종료 경합이었다. 해당 fixture의 요청마다 독립 연결을 사용하도록 수정했고 assertion이나 운영 코드는 바꾸지 않았다. 수정 후 해당 파일 전체 5/5를 두 차례 통과했다. 전체 1,058건을 수정 뒤 다시 실행한 결과로 표현하지 않는다. 집계 10건, 용량 마이그레이션 2건, 화면·탐색 49건과 TypeScript 검증도 통과했다. 마지막 SDK 보강 후 전체 SDK 테스트와 실제 Worker 프로토콜 통합 테스트를 함께 재실행한 결과는 59/59 통과·생략 0이다.

설치된 QA SDK는 저장소 제한 시간 200ms 버전이다. 느린 첫 실행에서 보고기가 초기화되지 않은 경우와 실행 확인 두 이벤트가 다음 정상 실행에서 전송되는 경우를 관찰했다. 실제 서버 최종 집계와 비워진 대기열을 확인한 뒤 성공으로 기록했다. 후속 SDK 소스에서는 저장소 제한 시간을 1,000ms로 늘리고, 기존 요청 전송 중 추가된 실행 확인 이벤트를 동일 flush의 남은 배치에서 처리하도록 개선했다. 최대 4개 배치와 실패 backoff는 그대로다. 이 후속 개선은 결정적 경합/지연 저장소 회귀 테스트로 확인했으며 이번 여섯 QA 번들에 포함됐다고 주장하지 않는다.

위 내용은 첫 배포 시점의 기록이다. 이후 보강 SDK를 세 앱의 새 GitHub 커밋으로 PC Runner에 배포하고 Android에서 추가 실행 없는 보고까지 확인한 결과는 [후속 실제 번들 검증](sdk-immediate-report-2026-10-15.ko.md)에 따로 기록했다.
